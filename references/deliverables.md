# Deliverables

## Complete guide

Keep the main plan usable on a phone. Include, as relevant:

1. title, update date, dates, people, budget scope, pace, and route concept;
2. overview table with day, areas, core stops, meals, lodging, steps or driving, and cost;
3. daily timelines with duration, transit, rest, cost, reservation, access rules, risks, and Plan B;
4. exact restaurant branches with Dianping observations, dishes, queue, route reason, and nearby backup;
5. lodging-area comparison and real candidates by tier after the route is stable;
6. route map or leg list, including arrival and departure transport;
7. category and daily budgets, party total, per-person total, and buffer;
8. booking list, seasonal switches, safety notes, and checks at seven, three, and one day before departure;
9. recommended comfortable duration when the requested duration is compressed;
10. optional source appendix with retrieval dates.

When the user asks for a clean guide, remove inline citations from the narrative while retaining the evidence ledger. Distinguish confirmed facts, estimates, and `【待确认】`.

## Presentation

For a final executable guide, build the deck only after route and budget audits pass. A user-requested draft or validation deck may show unresolved routes, but must label them as blocked or pending rather than approved. Use Presentations for PPTX. A practical deck has 10–18 slides:

- cover with destination, dates or season, people, budget, and route concept;
- route overview and a readable regional map;
- one chapter or timeline slide per day or route segment;
- explicit rest, fuel or charging, toilet, and meal points on long-drive slides;
- restaurant points with exact branches, current rating or review summary, average spend, dishes, and backup;
- lodging bases and why each reduces travel;
- budget chart with categories, per-person and party totals, buffer, and included scope;
- comfortable-duration or route-option comparison;
- booking, weather, road, safety, and pre-departure checklist.

Use a destination-derived palette and consistent 16:9 system. Keep slides decision-oriented. Use real venue imagery only with source provenance. ImageGen may create cover art, textures, dividers, or schematic ambience; label it as illustrative and never use it as proof of a real location, room, dish, or road condition.

Open the final PPTX in WPS or the user's target app and inspect every slide in slideshow view. Fix clipping, awkward line wraps, stretched images, illegible maps or charts, and inconsistent spacing. Recheck modified slides and validate the PPTX package before delivery.

Use the current presentation skill's runtime discovery and finalization workflow. For native tables, align required-table declarations with the actual slide numbers. For newly authored charts, package editable data/workbooks as required; do not replace an existing workbook merely to satisfy validation. Pass required runtime dependencies to validation subprocesses. Inspect the report's actual schema before reading result fields instead of assuming a key such as `finalPath` exists.

Record the final file hash, checked slide numbers, target app, structural/layout results, and remaining limitations. Validate the same final file that is delivered; a later edit invalidates the previous checks for affected content. Separate screenshots captured from slides actually inspected. A successful export or render is not a WPS check, and success in one local app version is not universal compatibility. If the target app cannot open the file through its picker, try a supported system file-opening route before reporting the check blocked.
